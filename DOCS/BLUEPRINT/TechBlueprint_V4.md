# COO Task Management Tool — Revised Specification v3

Spec plus architecture, Trello integration details, tool list and project skeleton.

## 1. Description

The agent automates team task management. The worker interacts with a bot as his/her assistant. Through audio or text input, the agent sets a new task, monitors it and manages it.

**Features:** create a new task; edit it (delete, set as done, move date, modify); monitor deadlines; notify the worker.

**Design principles.** Only use an LLM where language understanding is needed; everything else is deterministic code. Trello is the single source of truth for tasks. No write to Trello without a confirmation from the user. Every event is processed exactly once.

## 2. Architecture and agent list

### 2.1 Components

| Original component | Revised | Type | Reason |
| --- | --- | --- | --- |
| Director Agent | Orchestrator | LLM | Decides intent (create / edit / complete / move / query) and calls Trello search tools to resolve which card is meant. |
| Subagent 1: Notifier (SimpleX) | SimpleX Gateway | Code | Pure I/O: receives user messages, sends notifications. No reasoning needed. |
| Subagent 2: Transcriptor | Transcriber | Code | Whisper runs only if the input is audio. Transcript is passed directly to the next step. |
| Subagent 3: Task definer | Merged into Orchestrator | LLM | Extraction and intent are one reasoning step. Output is a structured Task object. |
| Subagent 4: Dispatcher | Queue / event bus | Code | Routing does not need an LLM. A SQLite or Redis queue gives retries and idempotency. |
| Subagent 5: Trello Manager | Trello Service | Code | API wrapper plus webhook receiver. Emits notification events. |
| (missing) | Scheduler | Code | Trello does not push deadline-approaching events, so reminders must be generated by us. |
| (missing) | Confirmation loop | Code | Asks the user to confirm before any write. Protects against noisy voice transcripts. |

### 2.2 Flow

- **New file dir.** The transcript goes straight to the Orchestrator and is archived to kDrive afterwards.
- **The Orchestrator reads existing state.** "Move the supplier call to Friday" only works if the agent can search open Trello cards and resolve the right one. It needs read tools, not just a form to fill.
- **Confirmation step.** Before writing, the bot replies e.g. "Create task 'Call supplier' for Marco, due Fri 23 Oct. OK?". Mandatory for delete and for any ambiguous match.
- **Archive instead of delete.** Deletion is implemented as archiving the card (recoverable).

### 2.3 Structure

SimpleX Gateway (in/out)
-> Transcriber (Whisper, only if audio)
-> Orchestrator LLM (intent + extraction, with Trello read tools)
-> Confirmation loop with user (pending actions in DB)
-> Trello Service (API wrapper, writes)

Trello webhook receiver --->
Scheduler (deadlines) ---> Notification builder --> SimpleX Gateway

Shared: Queue/DB (user mapping, processed IDs, pending confirmations)

## 5. Confirmation and pending actions

Every write action is stored in the `pending` table and applied only after the user confirms.

### 5.1 Pending lifecycle

1. **Creation.** After the Orchestrator returns a Task object, it is saved as pending with a unique `pending_id`, the requesting user and a `created_at` timestamp. A confirmation message is sent to the user.
2. **Confirmation window.** 24 hours. Unconfirmed pending actions expire after this window.
3. **Reminders.** While a pending action is awaiting confirmation, the Scheduler sends up to **3 reminders every 7 hours**. Reminders are only sent during daytime hours: **no reminder is ever sent between 02:00 and 05:00 Europe/Berlin**; if a reminder slot falls in that window it is deferred to 05:00.
4. **Expiry.** After 24 hours the pending action is **cancelled** and the user receives a notification: *"Your pending task was not confirmed within 24 hours and has been cancelled."*
5. **Confirmation.** A user reply confirming the pending_id pops it from the queue and applies it to Trello (write happens only here).

### 5.2 Idempotency and mark_processed semantics

`mark_processed(msg.id)` means: *this incoming message has been handled and must never be processed again*. It is **not** a confirmation and does **not** complete the workflow.

- `mark_processed` is called immediately after the pending action is saved (or the clarification question is sent), in the same transaction. If the process crashes before this point, the message is safely re-processed on retry; after this point, a retry cannot create a duplicate pending action.
- A message marked processed leaves its pending action in `pending` state until the user confirms or the 24-hour window expires. Marking processed ≠ action executed.
- The confirmation message from the user is itself a message with its own ID, and is marked processed after the Trello write is applied. A duplicate confirmation (e.g. same text sent twice) is therefore ignored.

### 5.3 Concurrency: FIFO

- **FIFO applies to ingestion only.** Incoming messages per user are transcribed, interpreted and turned into pending actions strictly in arrival order (single FIFO queue per user).
- **Each message is an independent process.** A message always contains either a new task or a modification. One pending action never blocks the next: while message 1's action is pending and unconfirmed, message 2 is taken in charge as its own process, with its own pending_id, its own 24-hour window and its own reminders. There is no limit of one active pending per user.
- **Confirmations are bound to a pending_id.** Each confirmation message from the bot includes a reference to its pending action (e.g. "Task #A3: Call supplier, due Fri. OK?"). A reply confirming that reference applies that specific action.
- **Ambiguous confirmation.** If the user replies with a bare "OK" while two or more pending actions are active, the bot does not guess: it asks which one is meant, listing the active pending actions with their references.
- Back-to-back voice messages are handled by the same FIFO: each is transcribed and interpreted in order; a message that was intended as a confirmation is matched against a pending_id before being treated as a new instruction.

## 6. Trello integration: can everything go through the API?

### 6.1 Authentication

Create an API key (Power-Up admin) and generate a token with read/write scope. Use a dedicated "Task Bot" Trello account so bot actions can be told apart from human ones.

### 6.2 Editing tasks

| Operation | Endpoint | Key parameters |
| --- | --- | --- |
| Create | POST /1/cards | idList, name, desc, due, idMembers, idLabels |
| Modify / move date / set done / move list | PUT /1/cards/{id} | name, desc, due, dueComplete, idList, idMembers |
| Archive (recommended) | PUT /1/cards/{id} | closed=true (recoverable) |
| Permanent delete | DELETE /1/cards/{id} | Irreversible, avoid |
| Read / search | GET /1/boards/{id}/cards, GET /1/search | Used by the Orchestrator to resolve cards |
| Comments, checklists, members | Dedicated endpoints under /1/cards and /1/boards | Optional extras |

### 6.3 Incoming events (Trello to the system): webhooks

- Register with POST /1/webhooks giving idModel (board, list or card) and a public HTTPS callbackURL.
- Trello posts a JSON action for each change: card created, updated (due date, list move, completion), commented, member added.
- The endpoint must answer Trello's initial HEAD request and should verify the HMAC-SHA1 signature header on every call.
- Webhooks can be disabled after repeated delivery failures: add a health check that re-registers them, plus a periodic heartbeat verifying the webhook is still active.
- Webhooks also fire for the bot's own edits. Ignore events whose actor is the bot's member ID to avoid loops.
- Human edits made directly in Trello arrive through the same webhook and become notifications to the people involved.

### 6.4 Limits to design around

- **Reminders.** There is no webhook event for an approaching deadline. Trello's own due reminders go to Trello's channels (app, email), not to our endpoint. The Scheduler fetches cards with due dates and sends reminders itself through SimpleX.
- **Outgoing messages.** Trello has no chat API. All user notifications go through SimpleX, built by our Notification builder.
- **Rate limits.** Roughly 300 requests per 10 s per API key and 100 per 10 s per token. Ample for a team, but prefer webhooks over polling.

## 8. Requirements (decisions)

| Requirement | Decision |
| --- | --- |
| User mapping table | SimpleX contact, Trello member, role. If a named assignee cannot be resolved, the bot asks a clarifying question. |
| Date handling | Relative dates ("next Tuesday") resolved in **Europe/Berlin**. |
| Languages | **English only**, for input, for Whisper and for the LLM prompt. |
| Idempotency | The same message must never create two cards or two pending actions (see 5.2). |
| Confirmation expiry | 24 hours; 3 reminders every 7 hours, daytime only (never 02:00–05:00 Berlin); on expiry the action is cancelled and the user is notified. |
| Concurrency | FIFO for ingestion only; every message is an independent pending process (no single-pending limit); confirmations bound to pending_id, ambiguous "OK" with multiple active pending triggers a clarification. |
| Error handling and retries | Failed transcription, Trello downtime, LLM errors, with a clear message to the user. |
| Permissions | Who may assign tasks to whom, who may archive or delete. |
| Privacy / GDPR | Retention of audio files and transcripts, where they are stored, who can read them. |
| Ambiguity policy | What the bot does when several cards match, or no assignee is named. |
| Trello board design | Lists, labels and who owns which board, so the Task object maps cleanly. |

## 9.1 Core data flow in code (outline)

```python
async def handle_incoming(msg):
    await queue.push(msg.sender, msg)            # FIFO per user

async def process_user_queue(sender):
    msg = queue.pop(sender)
    if db.already_processed(msg.id):            # idempotency
        return
    text = msg.text or await transcribe(msg.audio)
    user = users.by_simplex_id(msg.sender)      # permissions + mapping

    if confirm.is_confirmation(msg, sender):    # confirmation of a pending action
        task = pending.pop(msg.pending_id)
        result = trello.apply(task)             # create/update/archive
        db.mark_processed(msg.id)               # message fully handled
        await archive.save_transcript(task)
        return await gateway.send(user, render_result(result))

    task = await orchestrator.interpret(text, user)  # LLM + Trello read tools
    if task.needs_clarification:
        db.mark_processed(msg.id)               # question sent, no pending saved
        return await gateway.send(user, task.question)

    p = pending.save(sender, task)             # its own process, its own ID
    db.mark_processed(msg.id)                   # same transaction, no dup on retry
    await gateway.send(user, render_confirmation(p))  # includes pending ref

async def on_pending_confirmed(user, pending_id):
    task = pending.pop(pending_id)
    result = trello.apply(task)
    await archive.save_transcript(task)
    await gateway.send(user, render_result(result))

async def pending_reminder_job():               # hourly
    for p in pending.due_for_reminder():        # pending at 7h, 14h, 21h
        if 2 <= now_berlin().hour < 5:          # night window: defer
            continue
        await gateway.send(p.user, render_reminder(p))

async def pending_expiry_job():                 # periodic
    for p in pending.expired(24 * 3600):
        pending.cancel(p)
        await gateway.send(p.user, render_cancelled(p))
```

## 9.2 Suggested build order

1. Trello service and Task schema, tested against a sandbox board.
2. Orchestrator with text input only, including card search and confirmation loop.
3. SimpleX gateway with FIFO queue, so the bot works end to end with text.
4. Pending lifecycle: confirmation, 24h expiry, 3 daytime reminders, cancellation notice.
5. Whisper transcription for audio (English only).
6. Webhook receiver, loop prevention and notifications for human edits.
7. kDrive archive, GDPR retention rules, deployment and monitoring.
